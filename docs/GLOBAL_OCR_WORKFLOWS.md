# Reviewed document reading across the application

This branch extends the existing local OCR engine; it does not add an external AI upload provider. All reading results are proposals. The existing domain writers retain authority over customer creation, inventory changes, expenses, stock receipts, permissions, approved amounts and payments.

## Entry points and implemented workflows

| Enhancement | Entry point | Behavior |
| --- | --- | --- |
| Claims amount safety and common review | Claims Workspace → Carrier Estimate; shared review panels | Uploading evidence no longer writes an approved amount. Labeled totals become proposals; conflicting totals are not resolved by choosing the largest. Staff record approval with supporting evidence and a note. Existing unreviewed stored values remain in history and are presented as proposals, without modifying original records. |
| Scan-first spending | Money & Resources → Record spending | Read a receipt, correct fields, check totals and apply to the expense form. The same reviewed file is queued for attachment on save. Exact merchant-name matches suggest an existing vendor; existing form values require replacement confirmation. Identical receipts already attached within the viewer's spending scope block applying another expense from the reader and link to existing spending. Similar merchant/date/amount records also warn. Funding, business purpose and vehicle/RO links remain staff decisions. |
| Unified customer capture | CRM Next → individual/business intake → Capture Hub; `/capture/customer` | Desktop intake now invokes the working front/back ID capture directly. Conflicting ID fronts/backs are not copied automatically. Existing name/address entries require confirmation before replacement. Full ID numbers and ID images are not retained by this intake; only the existing masked/last-four fields are used. Business-card proposals can populate contact fields after review. Individual and business drafts stay separate. |
| Inventory/vendor OCR depth | Inventory Import → Documents; vendor invoice reading | Inventory PDFs are read page by page, up to 28 pages, through existing reviewed import/correction/history controls. Vendor direct invoice PDFs read every page within the existing 24-page limit and direct multi-invoice packets to batch processing. Blank pages are explicit exceptions. Existing duplicate, allocation, approval and historical-vehicle controls remain. |
| Parts, claim authorization and sales-document checks | Parts Receiving; Claim Customer Permissions; Sales Documents → Scan | Parts rows match exact part numbers and PO numbers before preparing receiving lines; actual receipt/condition/bin confirmation remains separate. Claim authorization suggests printed signer/date fields and retains the selected PDF on verified upload; consent, authority and signatures remain manual checks. Sales reading rejects a mismatched VIN before preparing a PDF for its jacket. Signature/POA acceptance and finalization remain separate. |

Statement rows can be corrected, prepared as a stable-source CSV and imported through existing card-transaction controls for matching. This does not create expenses or send payments. |

`/capture/documents` is a shared reading/review/export workspace for all twelve purposes. Capture Home and Document Library link to it. Standalone reading exports source-page information and file checksums; it does not save business records or retain the original file. Original documents remain in the current browser session until attached through their destination's existing document workflow. Spending, claim authorization and sales flows queue the reviewed original for their existing save/upload operation. Other workflows must retain the supporting original through their existing evidence controls.

## Limits and completeness

- Sales-document camera assembly, PDF upload validation and structured sales OCR support **1–28 pages per document**, retaining the 25 MB limit. The generic camera scanner keeps its default 12-page limit unless a workflow explicitly requests another supported limit.
- Spending receipts retain the existing PDF/JPEG/PNG and 10 MB attachment policy, with up to 10 pages for reading. Vendor packets retain 24 pages. Other document-reading profiles allow up to 28 pages.
- PDF reading splits copies into individual pages for extraction, leaving the original bytes unchanged. It rejects oversized packets before OCR starts and reports how many pages yielded text. It never silently treats an unread final page as complete.
- Generic document classification now recognizes receipts, purchase paperwork, vendor invoices, parts documents, title, transport, warranty, statements and sales/claim-authorization paperwork in addition to the original ID/business-card/estimate categories.
- Generic persisted ID intake masks license numbers to the last four and omits raw ID OCR text. Existing stored records are not rewritten. Classification scores remain parsing heuristics and are labeled as such.

## Review and data protection

The authenticated, same-origin reading endpoint checks workflow access and requires manager access for statements. It validates file size and signatures, disables response caching, hides engine diagnostics, and permits one active read per account per server process. It reads only the uploaded file; it does not fetch private documents from arbitrary IDs or URLs. Expense duplicate queries follow employee/manager and organization scope.

The shared panel shows original-file preview, source pages, editable fields/rows, conflicting candidates and reconciliation warnings. Editing invalidates confirmation. Existing non-empty form values are preserved unless replacement is confirmed. CSV exports quote values and protect against spreadsheet formula injection. Payment, consent, signer authority, title readiness, actual delivery, stock condition and canonical identity are never inferred as completed actions.

These are bounded, label-based document adapters using the local extraction engine, not a promise to understand every supplier layout, handwriting, damaged image or bank format. Unknown/conflicting information stays blank or requires correction. OCR is synchronous and holds reviewed drafts in the current page; persistent background processing and cross-device continuation for this generic reader are not claimed. Existing inventory import history and sales phone handoff remain available in their own workflows.

## Verification

`src/tests/unit/global-document-reading.test.ts` covers page-28 reading, page-29 rejection, source provenance, conflicting totals, parts arithmetic, statement signs and purpose-specific proposals. `document-reading-route.test.ts` covers authentication, workflow access, same-origin/size checks, scoped duplicate discovery and non-cached diagnostic-safe responses. Existing claims tests now assert that evidence cannot approve amounts; explicit staff approval remains supported. Scanner assembly verifies a real 28-page PDF. `scripts/check-global-document-reading-ui.mjs` exercises desktop/mobile review, preservation/replacement of existing values, reconciliation, source-file retention and the 28-page sales choice with fictional data and accessibility checks.

No migration is required. Existing approvals, invoices, signed documents and source history are not rewritten by this enhancement. Deployment and representative real-document acceptance remain separate from code verification.
