# Vendor billing and monthly agreements

Implemented on `codex/enterprise-general-refinement` for every vendor registry profile at `/customers/vendors/[vendorId]`. No vendor name controls behavior. Configure the actual terms for Simba Collision, Gil Tires, or any other vendor; the implementation does not invent balances or agreements for them.

## Staff workflow

The compact **Billing & monthly agreements** panel has Invoices, Agreements, Payments, Work review, and History views. **They owe us** and **We owe them** are separate balances. Collect/pay through today includes overdue amounts and currently due installments. Period views use Chicago business dates: today, yesterday, this week, last week, two weeks ago, this month, last month, and all dates. Invoice issue dates and installment due dates are separate filters. Export includes all filtered invoices, not only the current page.

1. **Bill vendor** records an outgoing invoice draft. **Receive vendor bill** records the supplier's original number and source reference. Existing vendor Documents uploads can be referenced. Staff may capture drafts; managers approve financial actions.
2. Add one line per vehicle/work ticket or fill lines from a repair batch. Several batches may remain open at once. Tickets remain associated with their selected batch; closing a batch does not automatically post a payable or imply payment.
3. In **Work review**, a manager links the shared vehicle, records the approved estimate/supplement amount and acceptance evidence, and confirms actual acceptance/QC. Posting and outgoing payment allocation check this saved scope against the current ticket and blocks aggregate billed work above the approved amount. Non-vehicle bills need an explanation. Acceptance is a human attestation; this does not automatically certify the separate repair-order QC system.
4. Managers may edit a draft, approve/post it, dispute or resolve it, or void an unposted draft. Posted amounts are preserved; use a credit adjustment rather than rewriting history. Draft changes retain an audit snapshot and invalidate stale versions.
5. Record actual money received or paid, including bank/check references, partial amounts, or unapplied cash. Apply remaining cash later using its actual allocation date. Reconcile explicitly against bank evidence. These records do not initiate bank transfers.
6. An **offset** requires an explicit mutual agreement reference and equal approved allocations in both directions. Balances are never silently netted. Reversing a payment, credit, or offset keeps the original record and posts the opposite allocations. This corrects the vendor ledger; it does not perform a bank refund.
7. Print invoices, supplier bill records, receipts/remittances, credits, offsets, reversals, monthly/repayment schedules, and dated account statements. Use the browser's Print / Save as PDF. Use **Set follow-up task** to schedule collection, missing documentation, or dispute work in the existing vendor task workflow.

## Invoice scanning and upload

On the vendor profile, **Documents → Scan invoice / Upload invoices** receives PDF, JPEG and PNG sources, reads every page, suggests invoice groups and opens prepared invoice reviews automatically. The existing **Bill / statement → Read invoice and fill billing** upload uses the same flow. Staff can select up to 12 files (10 MB each, 40 MB combined, 24 pages per file). Identical source bytes for this vendor reuse the saved document even if renamed. Original photos are retained; derived PDFs are used for page preview and invoice evidence. Several uploaded files stay in one intake batch after the first invoice is approved. For an already uploaded document, including a General document, use **Process into batch** beside the file.

**Process into batch** defaults to the current open batch and allows another open batch for the same vendor. If none exists, reading remains enabled and a prepared intake batch is offered; it is created only when an invoice is approved. **Read all invoice pages** processes every page, up to 24 pages/10 MB. Distinct recognized invoice numbers suggest new groups; unidentified continuation pages stay with the preceding group. For existing uploads, staff can confirm or correct the complete ordered page partition (for example `1-2; 3; 4-5`) before invoice review. New uploads open the suggested groups directly. Blank/unreadable pages remain included with warnings. Two separate invoices on one physical page require a separately prepared source; the app does not invent within-page boundaries. Suggested grouping is not a guarantee of detection.

The OCR text-quality gate rejects binary image-stream noise and falls back to OCR. Visual word coordinates restore label/amount row order across columns. An incomplete OCR reading receives one bounded higher-resolution retry. Inline invoice numbers, header dates and printed vehicle references are supported. If detailed item rows do not reconcile, an explicitly printed subtotal may be prepared as one cost line only when subtotal plus printed tax exactly equals the printed total. The source retains all part/labor detail.

When the invoice identifies one printed vehicle and no matching batch work ticket exists, intake prepares a vendor work-ticket proposal with vehicle reference, category, description, invoice-derived proposed service date and invoice cost. Approval creates the work ticket, batch if needed, draft bill, source-page evidence, batch link and audit record in one transaction. These are unverified inventory references and unaccepted work; no approved estimate, canonical inventory identity or QC attestation is invented. Duplicate vehicle references within the target batch require staff to select the existing ticket. An exact unique ticket/VIN can allocate all invoice work lines as a review suggestion.

Missing due dates stay empty unless staff explicitly confirm **For this intake, use the invoice date as the due date only where no due date is printed**. This review policy applies across the intake and its basis is retained in source metadata. A labeled but unreadable tax amount can offer a *calculated candidate* (printed total minus printed subtotal) only when no other adjustments appear between them. Tax stays empty until staff explicitly verify that candidate against the original. Its calculated/reviewed basis is retained; it is never represented as extracted text. Missing/conflicting facts without a safe proposal remain exceptions requiring correction. After approval, the next invoice opens automatically.

Review each invoice's original page subset, fields, totals and selected-batch work-ticket matches, then choose **Apply reviewed invoice to batch**. The app reconstructs those pages from the authorized original on the server. A serializable transaction retains the derived invoice PDF with original-document/page metadata, creates its received bill draft and due item, writes a persistent vendor-record invoice-to-batch link, and records the billing audit event. The original uploaded document is unchanged. Duplicate invoice numbers, identical files and overlapping previously imported source pages are blocked. Closed/foreign batches and work tickets outside the chosen batch are rejected. Stable request hashes include the reviewed fields, source bytes, page group and batch. A failure affects only that invoice; saved/skipped/pending counts make partial packet completion visible.

The active batch and batch ticket history show **Invoices applied to this batch** and the draft/posted total; disputed/void invoices are excluded from the prefill total. **Fill batch closing fields from reviewed invoices** copies the reviewed amount and notes after confirming replacement of existing entries. Multiple invoices retain their own invoice numbers/dates in billing, so the batch's single-number/date fields are left blank for multiple invoices. Batch closure remains an explicit separate action. The persistent batch link survives draft source-description edits. No schema migration is required by this enhancement.

OCR suggests invoice number, explicit invoice/due dates, separately stated tax, total and expense category. Exact vendor work-ticket, VIN and batch references suggest matches. Line items are suggested only when their integer-cent sum plus explicit or explicitly reviewed tax reconciles to the invoice total. Missing or conflicting values require review; today's date, unconfirmed net terms, work estimates and outstanding balances are not substituted. Vendor-name mismatches require staff confirmation; vendor master contact details are not overwritten.

Saving requires review and matching totals. One serializable transaction creates the original `BILL_STATEMENT` document, PAYABLE draft, due item and existing billing audit event. Source checksums reject identical files for the same vendor; normalized invoice-number uniqueness and stable request hashes protect retries. Invoice approval, work acceptance, payment and batch closure remain explicit existing actions. Draft lines link to selected work tickets, which retain their batch relationships; choosing a batch filters ticket choices and does not move tickets or close a batch. The billing list refreshes to **All dates** after import, so invoices due in future months remain visible.

OCR preview is authenticated, organization/vendor scoped, non-cached and does not persist raw extracted text. It uses the local document-text extraction service (Tesseract and Poppler for scanned PDFs), not a third-party AI upload. Production hosts must install/configure the existing OCR dependencies and allow sufficient request time. Direct-upload scanned PDF OCR uses the existing configured page limit (default 3, maximum 10), with a review warning. **Process into batch** extracts one original page at a time and reads all pages within the 24-page packet limit, so the shared page cap does not truncate packet analysis. Unavailable OCR leaves the source available for reviewed manual entry. Physical phone camera acceptance and representative vendor-layout acceptance remain necessary.

## Monthly obligations

- **Rent / recurring service:** monthly due dates preserve the original anniversary, clamping only in shorter months. **Generate due invoices** creates missing monthly drafts exactly once per agreement/month. A manager still approves each draft. Review backfilled periods after pausing/resuming an agreement; pausing does not erase existing obligations.
- **Existing debt repayment:** enter unpaid principal only if it has not already been recorded in this ledger. One opening balance is created, with up to 600 monthly installments and a reduced final installment. Installments do not generate repeated principal charges or represent new sales revenue.
- Gil Tires can have a receivable rent agreement alongside several payable vehicle-repair batch bills. Simba Collision can have an existing-debt repayment schedule alongside payable repair bills. Neither arrangement requires a second vendor profile.
- Missing recurring drafts remain counted on the account. An optional `npm run vendors:billing-worker` creates due drafts for active vendors using an active manager configured by `VENDOR_BILLING_WORKER_EMAIL`. It is safe to rerun because agreement/month uniqueness is enforced. Scheduling this command is an explicit deployment configuration step; no recurring job is activated by the code change. Failures produce a nonzero exit and identify the vendor requiring review.

## Controls and boundaries

Money is stored as integer cents. Financial commands run serializable transactions with vendor row locks, scoped foreign keys, request replay protection, optimistic document/agreement versions, and append-only event history. Duplicate invoice numbers are normalized within vendor/direction. Actual payment/adjustment references cannot be duplicated within the same vendor/type. Work-ticket ranges use a transaction-level reservation lock so concurrent multi-vehicle entry cannot overlap numbers.

Statement openings and closing balances use the actual allocation effective date, including reversals; applying old unapplied cash today does not backdate the application. Draft/void charges are excluded. Posted/disputed obligations remain visible separately from unapplied cash. The compact history shows the latest 100 events with staff names; all audit events remain stored.

This is the vendor operational billing subledger. It does not automatically post to Money & Resources, the general ledger, customer collections, or inventory costs, so staff must avoid recording the same actual movement twice across those workflows. It does not import old supplier bills, migrate the separate outside-repair-vendor directory, infer rent tax treatment, send invoices, collect payments, or draft a legally executed rental/debt agreement. Source documents and actual signed terms remain authoritative.
